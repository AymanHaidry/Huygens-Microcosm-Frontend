Why Did Concorde Fail Commercially?

Generated by Winery v2.0 • 12 sources consulted • Confidence: High

Executive Summary. The Concorde supersonic airliner failed commercially due to a convergence of economic, environmental, and operational factors that made it unsustainable despite its technological brilliance. The aircraft was never profitable for British Airways or Air France on a standalone basis, requiring government subsidies to remain in service.

Key Findings

1. Excessive Operating Costs. Concorde burned approximately 6,770 gallons of fuel per hour — roughly 3.5 times more per passenger than a Boeing 747. Ticket prices reached $12,000 for a round-trip transatlantic flight, limiting the addressable market to an extremely narrow elite segment.

2. Sonic Boom Restrictions. The aircraft was banned from flying supersonic over land, which eliminated the most lucrative routes (New York to Los Angeles, London to Tokyo) and confined it to the transatlantic corridor.

3. The 2000 Crash and Aftermath. The Air France Flight 4590 crash on July 25, 2000, killed 113 people and grounded the fleet for over a year. When service resumed in 2001, post-9/11 travel declines further eroded demand.

The Engine

What is Winery?

Winery is the autonomous research agent that powers Nanofossil. It is not a chatbot. It is a pipeline — a sequence of deterministic stages that transforms a raw question into a structured, sourced, cross-checked research report. It runs inside a GitHub Actions workflow, uses a locally-hosted Qwen3-4B model via llama-cpp-python, and costs exactly zero rupees per run.

Winery Agent

Orchestrates the entire pipeline. Plans, searches, fetches, synthesizes.

The Five Stages

1

Understand

Winery reads your question and decomposes it into 3–5 sub-questions or search angles. A question like "Why did Concorde fail?" becomes queries about operating costs, sonic boom bans, the 2000 crash, and ticket pricing.

2

Research

Each planned query is executed against DuckDuckGo. Top results are fetched and parsed into clean text. Winery strips ads, navigation, and boilerplate. What remains is the substance of the page.

3

Cross-Check

Sources are compared against each other. Conflicting claims are flagged. Dates are verified for consistency. Sources are tagged as primary (original documents, official reports) or secondary (news, analysis).

4

Synthesize

The Qwen3-4B model processes all gathered evidence and produces a coherent narrative. It weighs conflicting sources, notes where evidence is thin, and structures findings into logical sections.

5

Write

The final output is a structured JSON document: executive summary, key findings with evidence, confidence assessment, and a numbered source list. Committed directly to your GitHub repo.

Technical Details

How Winery Works Under the Hood

Winery is a Python package that lives in your GitHub repository. When you trigger a research run — either manually from the GitHub Actions tab or via the Nanofossil frontend — the following happens:

1. Workflow Trigger

The GitHub Actions workflow star1.yml (or nanofossil.yml) defines a workflow_dispatch trigger with one input: research_question. When triggered, it spins up an Ubuntu runner and checks out your repository.

name: Nanofossil Research
on:
  workflow_dispatch:
    inputs:
      research_question:
        description: 'What would you like to understand?'
        required: true

jobs:
  research:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Cache model
        uses: actions/cache@v4
        with:
          path: models/
          key: ubuntu-nanofossil-model-qwen3-4b-q4_k_m
      - name: Run Winery
        env:
          RESEARCH_QUESTION: ${{ github.event.inputs.research_question }}
        run: python winery/main.py

2. Model Caching

The first run downloads the Qwen3-4B-GGUF model from Hugging Face (~2.3GB for Q4_K_M). This is cached using actions/cache on the models/ directory. Subsequent runs skip the download entirely. The cache key includes the model name and quantization, so changing either invalidates the cache and triggers a fresh download.

3. The Research Loop

Once the model is loaded into memory via llama-cpp-python, Winery enters its main loop:

  1. Plan: The model generates 3–5 search queries based on the input question. These are not simple rephrasings — they target different angles (economic, technical, historical, comparative).
  2. Search: Each query is sent to DuckDuckGo via the duckduckgo-search Python package. The top 5–10 results per query are collected.
  3. Fetch: Winery fetches each result URL, extracts the main content using readability heuristics, and strips HTML, ads, and navigation. The result is plain text suitable for the model.
  4. Synthesize: All fetched content is fed back to the model with a structured prompt. The model produces the final report in JSON format.
  5. Commit: The JSON report is written to results/{run_id}.json and committed back to the repository via the GitHub API.

4. Output Format

Every report follows the same JSON schema:

{
  "question": "Why did Concorde fail commercially?",
  "executive_summary": "...",
  "key_findings": [
    {
      "claim": "Operating costs were 3.5x higher per passenger than subsonic jets",
      "evidence": ["British Airways Annual Report 2003", "..."],
      "confidence": "high"
    }
  ],
  "evidence_assessment": {
    "primary_sources": 4,
    "secondary_sources": 8,
    "conflicts_noted": 1
  },
  "sources": [
    { "id": 1, "title": "...", "url": "...", "type": "primary" }
  ],
  "generated_at": "2026-08-16T14:32:00Z"
}

5. Frontend Integration

The Nanofossil frontend does not run Winery itself. It triggers the GitHub Actions workflow via the GitHub API using your Personal Access Token, then polls for completion. When the workflow finishes and commits the result, the frontend fetches the JSON and renders it as a readable report.

This separation is intentional: the frontend is a thin, static shell. All the heavy lifting — model inference, web search, text extraction — happens on GitHub's infrastructure. You could use the frontend from a phone and run research on a serverless backend without ever deploying a server.

6. Limitations & Honesty

Winery is not magic. It is a 4B parameter model running on a free-tier VM with limited context. Here is what it cannot do:

  • No real-time data: It searches the web, but DuckDuckGo results have latency. Breaking news from the last hour may not appear.
  • No PDF extraction: It cannot read academic PDFs. It relies on HTML pages and text extracts.
  • Limited context: 8192 tokens sounds like a lot, but with 5 queries × 10 results × ~500 tokens each, content must be aggressively summarized before synthesis.
  • 4B quality ceiling: Qwen3-4B is impressive for its size, but it will hallucinate details, misattribute quotes, and occasionally generate confident-sounding nonsense. Always verify critical claims.
  • ~15 minute runtime: GitHub Actions free tier has a 6-hour limit, but model loading + search + synthesis typically takes 10–15 minutes per question.
  • DuckDuckGo rate limits: Cloud IPs sometimes get blocked or rate-limited by DuckDuckGo. If searches return empty, wait and retry.

Getting Started

Setup in 10 Minutes

No server. No credit card. No API bills. Just a GitHub account and a browser.

Backend (Winery)

  1. Fork or clone the Huygens-Star1 repository (or create your own with the Winery files).
  2. Push the winery/ directory, requirements.txt, and .github/workflows/star1.yml to your repo.
  3. Run a test: Go to Actions → Star1 → Run workflow. Enter "test" as the question. This verifies model download and loading.
  4. Run real research: Trigger the workflow with any question. Wait 10–15 minutes. Check the results/ directory.

Frontend (Nanofossil)

  1. Deploy this HTML (and the associated CSS/JS) to Vercel, GitHub Pages, Netlify, or Cloudflare Pages. It is pure static files.
  2. Configure Supabase: In Settings → Supabase tab, enter your project URL and anon key. Click Save & Connect.
  3. Configure GitHub: In Settings → GitHub tab, enter your PAT (with repo and actions scope) and the repo slug where Winery lives.
  4. Sign in with email or GitHub, then ask your first question.

FAQ

Questions & Answers

Why is it called "Nanofossil"?
A nanofossil is a microscopic fossil — something tiny that preserves a record of something much larger. The name reflects the idea that each research run is a small, preserved snapshot of knowledge at a point in time. It also continues the Huygens naming convention (Microcosm, Star1, Nanofossil).
Is this really free?
Yes. GitHub Actions free tier gives you 2,000 minutes per month. A typical Nanofossil run takes 10–15 minutes. That is ~130–200 research runs per month at zero cost. The model is downloaded once and cached. Supabase free tier handles auth and history. No paid APIs are used.
Can I use a different model?
Absolutely. Change the MODEL_REPO and MODEL_FILE environment variables in the workflow. Any GGUF model on Hugging Face will work. Just ensure it fits in the runner's 7GB RAM. Llama 3.1 8B Q4_K_M (~4.5GB) has been tested and works, though it leaves less headroom.
What if DuckDuckGo blocks the runner IP?
This happens occasionally with cloud IPs. The workflow will show a warning: "Very few sources found." You have a few options: (1) retry later, (2) add a fallback search provider like Brave Search (requires API key), or (3) run Winery locally on your machine where your residential IP is trusted.
Can I run this entirely locally?
Yes. Clone the backend repo, install requirements, download the model, and run RESEARCH_QUESTION="your question" python winery/main.py. The output will be written to a local results/ directory. You do not need GitHub Actions, Supabase, or the frontend.
How accurate are the reports?
They are a starting point, not a final authority. The 4B model can hallucinate, misattribute, or oversimplify. Always verify critical claims against the listed sources. Winery is designed to give you a structured map of the territory — you still need to walk it.
What happened to "Star1"?
Star1 was the original codename. Nanofossil is the evolution — same architecture, same Winery engine, but with a clearer identity, better documentation, and a more polished frontend. The backend repositories remain compatible.
